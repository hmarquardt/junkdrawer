Orientation

Pick the infrastructure by requirements, not by habit.

Describe a workload, and this workbench eliminates the options that cannot meet its hard constraints, ranks what remains on operational consequences, prices each survivor, and tells you what would have to change for the answer to change.

Evidence dated 2026-10-10

Orientation

How the engine decides

Four stages, in order: feasibility, operational suitability, economics, recommendation. Hard constraints are binary and evaluated first. Weighted preference scores only ever compare options that already passed.

Orientation

The building blocks on the table

Every candidate is described by the same fields, so it can be tested against the same requirements. These are execution and storage primitives, not products to be admired.

The workbench

Workload Architect

Start from a template or from nothing. Only the first group of fields is required; the rest sharpen the answer and are revealed when they can change it.

The workbench

Architecture comparison

Cards from the last evaluation, plus a side-by-side view of any two or more candidates. Suitability is qualitative; feasibility is evidence-based.

Run the Workload Architect first — there is nothing to compare yet. Comparison reads the current requirement set rather than inventing one.

The workbench

Topology inspector

A diagram per architecture pattern, drawn from the same edge data the engine uses — so a line exists only if the platform actually supports that relationship.

The workbench

Comparative cost model

Meters, allowances, pools, rounding and plan prerequisites — computed rather than estimated. Fixed baseline charges are kept separate from incremental usage.

The workbench

Break-even and sensitivity

Where one option becomes cheaper than another, and how the recommendation moves when a single assumption changes. Crossings are reported with the resolution they were found at, never as exact constants.

The workbench

Operational complexity and TCO

A three-dollar workload is a bad bargain if it needs a weekend a month. Direct cost, operational time, reliability risk and migration effort are shown separately, and the labour rate is yours to set.

Hybrid

GitHub and Cloudflare together

The usual division of labour — GitHub for disposable execution and versioned data generation, Cloudflare for request-driven serving and durable state — with the places where that division breaks down stated plainly.

Hybrid

Architecture pattern library

Concrete topologies with their components, data flow, cost drivers and the constraints that rule them out. These are what the engine actually recommends.

Practice

Scenario library

Thirty-six workloads with stated assumptions, a recommended architecture, a strong alternative, the cost drivers, the failure modes and a way to load each one into the architect.

Practice

Architecture reviews of my own projects

Read from repository configuration and documentation, not from the dashboards. Verified present state, main workloads, real constraints, alternative architectures, migration complexity and a recommendation with its confidence stated.

Practice

Constraint and failure analysis

Fifteen mismatches, each walked to a specific alternative. The purpose is to recognise the wrong architecture before writing it, not to collect error messages.

Reference

Saved scenarios, export and import

Requirement sets live in this browser only. The export format carries a schema version, contains no credentials, and is validated on import rather than trusted.

Reference

Evidence table

Every limit and price the engine reasons with, its plan applicability, its source and the date it was read. Hard documented limits and soft operational judgements are labelled differently, on purpose.

Sources and methodology

Where each number came from, how recommendations are produced, what this workbench deliberately does not know, and how it stays accurate as two fast-moving platforms change.
