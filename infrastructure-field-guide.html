Infrastructure Field Guide

Less infrastructure. Better decisions.

Four interactive technical guides exploring automation, application platforms, architecture selection, and the enduring role of hyperscale cloud infrastructure.

After decades of building software, working with cloud platforms, managing databases, and maintaining deployment pipelines, I’ve become increasingly interested in a simple question:

What’s the least complicated infrastructure that will reliably do the job?

Lately I’ve found myself gravitating toward GitHub for source control, automation, and ephemeral compute, and Cloudflare for application hosting, APIs, data storage, and distribution. Together they cover a surprising amount of territory.

But this isn’t a declaration that GitHub and Cloudflare are the only tools worth using — or even always the best ones. There’s a place for AWS and Google Cloud, certainly. There’s also a place for Railway, Vercel, Fly.io, Render, DigitalOcean, Supabase, conventional virtual machines, managed services, and sometimes just running a job on a computer I already own. The right answer depends on the workload, the economics, the operational burden, and what infrastructure already exists.

These four guides represent where my thinking has landed today — not a universal prescription for how everyone should build software. They’re part reference library, part experimentation laboratory, and part an ongoing attempt to challenge my own architectural assumptions.

The goal isn’t to eliminate cloud providers. It’s to stop paying — in money, complexity, or attention — for infrastructure I don’t actually need.

Right Tool for the Job

“Given a particular workload, what’s the most appropriate infrastructure?”

An evidence-based decision workbench. You describe a workload — memory, duration, data volume, concurrency, dependencies, environment — and it returns a recommendation with the alternatives it rejected and the reason for each rejection. Dated cost models, break-even analysis, operational total cost of ownership, hybrid GitHub/Cloudflare architectures, failure analysis, and reviews of eight real projects including several from this drawer.

Representative topics

  • Workload-first architecture selection
  • Technical feasibility and hard resource constraints
  • Cost comparison and break-even against a status quo
  • Operational complexity and maintenance burden
  • Hybrid architectures that split work across platforms
  • Reviews of the projects in this drawer

Interactive capabilities

  • Workload architect that produces a recommendation
  • Side-by-side comparison with rejected alternatives
  • Topology diagram for the chosen architecture
  • Break-even and TCO models you can drive
  • 36 worked scenarios and eight project reviews

Best for: a real decision with a real deadline — when you want a defensible answer with its reasoning attached, not a vendor comparison table.

Reference manuals

Guides 01 and 02

Broad, deep, and organised by platform. These are the pages you keep open in a second tab while you work: what a runner actually has, what D1 actually guarantees, what a cron trigger actually promises, what each of those things costs.

Used by the decision tools. The workbench links back to specific manual sections rather than restating them, so there is one place where a platform fact lives.

Decision tools

Guides 03 and 04

Narrow, opinionated, and organised by question. These are the pages you open when you have to choose something: they produce an answer, name the alternatives they rejected, and attach the reasoning so you can disagree with it.

They disagree with each other on purpose. The workbench recommends; the audit challenges. Where they contradict, the audit says so in public — see the nine disagreements.

And a real answer

Sometimes: nothing

All four guides are built to be able to conclude that the current architecture is fine and should not change. On this drawer’s own projects, that is the majority verdict, and it is the most useful thing any of them does.

05From the field

Findings from the field

These are the projects the collection was actually built around. Each one is a real configuration that was read, not a hypothetical, and each verdict below is the one recorded in the guides. Where a number is a measurement it is stated as one; where a verdict is uncertain, the uncertainty is reported too.

Overhead

Scheduled automation · GitHub Actions & Pages

A workflow runs at 06:23 UTC every day and at 06:17 on the first of the month, on an ephemeral Ubuntu runner with a 45-minute timeout and contents: write. It reads three public astronomical sources, validates them, and commits refreshed datasets only when a SHA-256 comparison shows something actually changed. It holds no secrets: authentication is the job’s own token. The published datasets and the site that reads them share one repository, so code and data version together, and a failed run leaves the last good dataset in place. On a public repository the whole arrangement costs nothing per month.

Lesson

A repository can be an automation platform as well as a place to store code.

Road Naturalist

Geospatial processing · local compute, edge endpoint

Heavy geospatial work — tens of millions of source features, a peak working set in the tens of gigabytes, hundreds of gigabytes of intermediate Parquet — stays on local hardware, while a small Worker answering page-validation requests handles the online part. The necessity audit ran nine execution options against that envelope and concluded that no hyperscaler is justified as the workload runs today. Both the audit and the workbench name the same missing ingredient: not compute, but a deadline. A rebuild with a deadline it could miss is the condition that would change the answer, and the pipeline is already partition-parallel with per-tile manifests, which is exactly what makes a Spot fleet safe if that day arrives. The workbench’s open question is where the derived dataset should be served from.

Lesson

Moving computation into the cloud isn’t automatically an improvement.

Guide 04 · Road Naturalist case study  ·  Guide 03 · Road Naturalist review

CFLab

Application backend · Cloudflare Workers, D1, R2

One Worker written in TypeScript serves an API and a machine-facing surface. Two D1 databases hold relational data with numbered migration directories; a private R2 bucket is reachable only through the Worker binding; transactional email goes out through a send_email binding; five separate rate-limit namespaces guard login, recovery, reset, analytics and invitations. A second, independently deployable Worker serves its own dashboard from static assets, validates sessions through a named service-binding entrypoint rather than an HTTP route, and runs maintenance on an hourly cron. There is no container, no queue and no background server in the main Worker — and the parts that would traditionally have been a database server, a file host and a mail relay are bindings.

Lesson

Serverless infrastructure can replace substantial portions of conventional application hosting.

JunkDrawer

Static publication · GitHub Pages, with R2 where it matters

This drawer publishes standalone single-file browser tools straight to GitHub Pages: no build step, no server, and every tool opens from a local file as readily as from a URL. The one dynamic dependency is a script tag pointing at an analytics collector, and it degrades to nothing when unreachable. Where a tool genuinely needs large data, that data already lives in object storage behind a custom domain rather than in the repository. The workbench reviewed it and recommended keeping it exactly where it is, on the grounds that nothing here needs request-time compute, and that the two places where Cloudflare genuinely helps are already using Cloudflare. Uploading the repository to a different host would be nearly trivial; owning a second deployment path would be the real cost.

Lesson

An existing simple architecture does not need migration merely because another platform offers more features.

Collecting Nichols

Containerised service · a managed container host

A container with a long-lived process, an attached database and a filesystem — the shape that scale-to-zero platforms handle least well. The workbench recommends staying, unless the workload turns out to be actually batch-shaped, and it says plainly that its confidence is low: it did not read the configuration in detail, and it names three things it would need — real resource usage, how often the process is idle, and how much state lives on the local filesystem. The strongest argument for moving is the cost of idle hours; the strongest argument against is state, because Cloudflare containers have no persistent filesystem, so a migration would rework persistence on top of a platform move.

Lesson

Architecture migration must deliver enough value to justify the work.

The nine disagreements

Self-audit · Guide 04 auditing Guide 03

The workbench ships 36 scenarios with written recommendations and a deterministic engine. The engine agreed with the written advice in 27 of them. The fourth guide reproduced all nine disagreements by running the workbench’s own engine headlessly against its own scenario library, then classified them: two implementation defects, three scoring or relevance weaknesses, two capability-data weaknesses, and two requirement-vocabulary problems rather than engine problems. In six cases the written advice was better supported by the evidence; in three, both answers are defensible. The audit also records a hypothesis it tested and discarded, and states that no file in the audited artifact was modified to make the agreement rate look better. The defects are documented, not patched — that is the point being demonstrated.

Lesson

A recommendation engine should be inspectable, testable, and willing to expose its own limitations.

06The rest of the market

Beyond GitHub and Cloudflare

This is not a disclaimer, and it is not a consolation prize. GitHub and Cloudflare feature prominently here because they are what I happen to have built on and learned well — not because they won a comparison. There is a large, healthy field of providers I would recommend without hesitation in the right circumstances.

Railway

Conventional application and container hosting

A developer-friendly path to running a container or a service with an attached database, without assembling the platform yourself. Deployments are a push, and the mental model is a small number of long-lived services.

Reach for it when an application already fits a conventional container or process model and moving it would add complexity rather than remove it.

Vercel

Frontend and framework-oriented deployment

Deployments, previews and edge delivery shaped around frontend frameworks. The workflow is the product: a branch becomes a reviewable URL, and the framework’s conventions are first-class.

Reach for it when the framework, the development workflow and the deployment model all point the same way, and the preview loop is worth more than portability.

Fly.io

Applications with regional placement

Runs ordinary application processes close to users, with a real filesystem and conventional runtime expectations. Placement is an explicit decision rather than an emergent property of a CDN.

Reach for it when geographic placement matters, or when the application behaves in ways an isolate cannot.

Render

Managed applications, databases and workers

Application hosting, managed data and background services from one dashboard, with the conventional service shapes most teams already know how to operate.

Reach for it when straightforward deployment and familiar service models are the priority, and the team would rather not learn a new execution model.

DigitalOcean

Understandable, controllable compute

Virtual machines, managed databases and application hosting with pricing and limits that are easy to reason about, and no serious abstraction between you and the machine.

Reach for it when a small, predictable fleet you can log into is exactly what the problem calls for, and predictability beats elasticity.

Supabase

PostgreSQL as the architectural centre

A managed PostgreSQL core with authentication, storage and the services that grow around a relational database. When the data model is relational and long-lived, that is a very good place to stand.

Reach for it when PostgreSQL is a requirement rather than an implementation detail, and you would rather not run it yourself.

A conventional VPS

One small persistent Linux instance

A few dollars a month buys a machine with a real filesystem, no execution ceiling, no cold start and no request-counting. It is unfashionable and frequently correct.

Reach for it when the job wants a daemon, a cron entry, a volume and a stock runtime — and you are willing to own patching it.

Local computing

The hardware you already own

A laptop or workstation that is idle most of the evening is a legitimate processing platform. Large data often costs more to move than to compute where it already is.

Reach for it when the workload is heavy, native, occasional, and already sitting next to the data. Ask what you would actually gain before uploading terabytes.

Two things this list is not

It is not exhaustive. Specialized GPU hosts, managed database providers, storage and CDN specialists, message brokers, observability vendors and serverless platforms are all better than anything here at something specific, and a serious architecture will usually use several of them. Nothing on this page should be read as a claim that GitHub and Cloudflare cover every requirement — the fourth guide exists precisely because they do not.

It is also not a price comparison. No live pricing is published on this page, deliberately: rates move, regions differ, and a number copied here would be wrong within a quarter. Where the guides do quote a rate, they date it and name the rate card it came from, and they let you override it with your own quote.

A good architecture decision does not begin by excluding most of the market. It begins by writing down what the workload actually requires.

08The working principles

The philosophy and its limits

These are the principles that actually inform the collection — the ones I use to judge my own work, not rules for anyone else. They are also the reason the fourth guide is allowed to answer “I can’t tell” and the third is allowed to answer “change nothing”.

Prefer simplicity, not minimalism

A simpler system that cannot satisfy the requirements is not the right system. Simplicity is a tiebreaker among architectures that all work, never a licence to skip a requirement.

Account for operational attention

A service that costs three dollars less and demands an hour of maintenance a month is usually the more expensive one. Attention is the scarce resource, and it does not appear on any invoice.

Respect the incumbents

Infrastructure that is stable and working has real value, and a migration is two projects: moving the thing, and re-earning the operational knowledge you already have. The burden of proof sits with the move.

Know the execution boundaries

CPU, memory, disk, wall-clock duration, scheduling, networking, consistency and availability requirements decide more architecture than any feature comparison. Write them down before shopping.

Recognize when managed is worth paying for

Database failover, private networking, compliance evidence, regional controls, specialized hardware and genuinely distributed computation can justify substantial infrastructure. The point is to pay deliberately, not to avoid paying.

Remain open to change

Capabilities, prices, limits and workloads all move. A conclusion reached eighteen months ago is a hypothesis with a birthday, and the guides print the dates that let you see how old they are.

Treat recommendations as hypotheses

Real measurements and production experience outrank elegant theoretical comparisons. The nine-disagreement audit exists because the workbench’s own engine needed checking against its own written advice.

Say when you cannot tell

“Insufficient information” is one of the five verdicts in the necessity audit, and it is a legitimate answer. A confident wrong recommendation costs more than an honest unknown.

This page: Infrastructure Field Guide, version 2026.10.10.1, last updated 2026-10-10. It was written on that date and has not been synchronised since; treat an older date here as a prompt to check the guides themselves.

  • Pricing and platform limits change. Every rate in the guides is dated and sourced, and none of them should be trusted more than the rate card they came from. The guides let you override any rate with a real quote, and they are built to say “unknown” rather than guess.
  • Architectural principles age more slowly than provider facts. The reasoning on this page — write the requirements down, count the operational attention, respect a working incumbent — is meant to survive a price change. The specific numbers are not.
  • The guides are independent single files. Each one embeds its own evidence, so a guide keeps working, and keeps its own dates, whether or not this landing page is ever updated.
  • Nothing here is fetched at runtime. This page renders from a snapshot bundled into the file, so it works offline and needs no API call to draw its navigation.

Nothing here stays in sync by itself

There is no automatic synchronization mechanism between the four guides, the registry and this page. The version numbers above were read from junk-drawer.json when this page was last written, and they will be stale the moment a guide is updated. That is a deliberate trade: a landing page that fetched the registry at load time would be a page that shows nothing when the network is unavailable, and it would still be describing evidence that is older than the fetch suggests.

When it matters, the authoritative record is the registry and each guide’s own “Sources” section, which carries per-rate read dates. This page is the map, not the territory.

About the author of these guides

One developer, working alone, on real projects: a celestial planner, a foraging tool, a wildlife road-cruise investigator, an application backend, a drawer of small browser tools. The guides exist because I kept answering the same infrastructure questions on each project and wanted the answers written down once, with their reasoning and their dates attached.

These are tools and conclusions I’ve arrived at through experience and exploration. They’re not the only correct answers, and they’re subject to revision as the evidence changes. If a guide recommends something that would not work in your environment, the useful thing to do is find the requirement it missed.
